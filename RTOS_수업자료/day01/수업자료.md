# 1일차 요약 자료

## 1. RTOS란?

RTOS는 Real-Time Operating System의 약자입니다. 한국어로는 실시간 운영체제라고 부릅니다.

RTOS의 핵심은 단순히 "빠른 운영체제"가 아닙니다. 더 정확히는 "정해진 시간 안에 예측 가능한 방식으로 작업을 처리하는 운영체제"입니다.

일반 PC나 서버에서 사용하는 운영체제는 여러 프로그램을 효율적으로 실행하고, 사용자 편의성과 전체 처리량을 높이는 데 초점이 있습니다. 반면 RTOS는 특정 작업이 정해진 시간 안에 실행되는지를 중요하게 봅니다.

## 2. 일반 OS와 RTOS 비교

| 구분 | 일반 OS | RTOS |
|---|---|---|
| 주요 목표 | 처리량, 편의성, 범용성 | 예측 가능한 응답 시간 |
| 작업 처리 | 여러 작업을 공정하게 처리 | 우선순위가 높은 작업을 먼저 처리 |
| 시간 보장 | 상대적으로 약함 | 상대적으로 강함 |
| 대표 환경 | PC, 서버, 모바일 | 임베디드, 장치 제어, 산업 장비 |
| 예시 | Windows, Linux, macOS | FreeRTOS, Zephyr, VxWorks, ThreadX |

중요한 차이는 "평균적으로 빠른가"가 아니라 "최악의 상황에서도 제한 시간 안에 반응할 수 있는가"입니다.

## 3. 실시간성의 의미

실시간성은 이벤트가 발생했을 때 시스템이 제한 시간 안에 반응하는 성질입니다.

예를 들어 키오스크에서 프린터 용지가 없다는 이벤트가 발생했다고 가정합니다. 이 상태를 늦게 감지하면 사용자는 결제 후 영수증을 받지 못할 수 있습니다. 장비 운영자는 장애를 늦게 알게 되고, 주문 흐름은 꼬일 수 있습니다.

실시간성은 다음 질문으로 판단할 수 있습니다.

- 이벤트 발생 후 얼마 안에 감지해야 하는가?
- 감지 후 어떤 작업을 먼저 처리해야 하는가?
- 늦게 처리되면 어떤 문제가 생기는가?
- 반드시 성공해야 하는가, 아니면 지연되어도 복구 가능한가?

## 4. Hard Real-Time과 Soft Real-Time

| 구분 | 의미 | 예시 |
|---|---|---|
| Hard Real-Time | 제한 시간을 넘기면 시스템 실패로 간주 | 자동차 에어백, 의료 장비, 모터 안전 제어 |
| Soft Real-Time | 지연되면 품질은 떨어지지만 복구 가능 | 영상 스트리밍, 키오스크 상태 보고, 로그 전송 |

키오스크는 대부분 Soft Real-Time에 가깝습니다. 다만 도어 열림 감지, 결제 장치 오류, 프린터 장애처럼 즉시 운영 상태에 반영되어야 하는 이벤트는 높은 우선순위로 다루어야 합니다.

## 5. RTOS 기본 개념

### Task

Task는 RTOS에서 독립적으로 실행되는 작업 단위입니다. 일반 프로그래밍의 함수와 비슷해 보이지만, Task는 스케줄러에 의해 반복적으로 실행되거나 대기 상태로 전환됩니다.

키오스크에서는 다음처럼 Task를 나눌 수 있습니다.

| Task | 역할 |
|---|---|
| ButtonTask | 물리 버튼 입력 감지 |
| CardReaderTask | 카드 삽입, 결제 상태 감지 |
| PrinterTask | 영수증 출력 및 프린터 오류 감지 |
| DoorSensorTask | 점검 도어 열림 감지 |
| ServerSyncTask | Spring Boot 서버로 이벤트 전송 |

### Scheduler

Scheduler는 어떤 Task를 언제 실행할지 결정하는 RTOS의 핵심 구성 요소입니다. RTOS에서는 보통 우선순위가 높은 Task가 먼저 실행됩니다.

### Priority

Priority는 Task나 이벤트의 중요도를 나타냅니다. 장애나 안전과 관련된 작업은 높은 우선순위를 가져야 합니다.

예시:

- 우선순위 1: 프린터 용지 없음, 도어 열림, 결제 장치 오류
- 우선순위 2: 결제 승인, 결제 실패
- 우선순위 3: 주문 버튼 입력
- 우선순위 4: 영수증 출력 완료
- 우선순위 5: 일반 상태 로그

### Queue

Queue는 Task 사이에서 이벤트나 데이터를 주고받는 통로입니다.

```text
ButtonTask
  -> EventQueue
  -> ServerSyncTask
  -> Spring Boot API
```

ButtonTask가 직접 서버와 통신하지 않고 Queue에 이벤트를 넣으면, ServerSyncTask가 이를 꺼내 서버로 전송할 수 있습니다. 이렇게 하면 장치 감지와 서버 통신의 역할이 분리됩니다.

## 6. 키오스크 시스템을 나누어 보기

키오스크는 화면 프로그램 하나로만 구성되지 않습니다.

```text
사용자 화면
  -> 주문 선택
  -> 결제 요청

Spring Boot 서버
  -> 주문 생성
  -> 결제 상태 관리
  -> 장치 이벤트 저장
  -> 관리자 조회 API 제공

RTOS Runtime
  -> 버튼 입력 감지
  -> 카드 리더 상태 감지
  -> 프린터 출력 처리
  -> 장치 장애 감지
  -> 서버로 이벤트 전송
```

역할을 분리하면 시스템이 명확해집니다.

| 영역 | 잘하는 일 | 맡기면 애매한 일 |
|---|---|---|
| RTOS | 장치 입력, 출력, 빠른 상태 감지 | 주문 정책, 회원 관리, 통계 |
| Spring Boot | 주문, 결제 상태, API, 데이터 저장 | 물리 장치의 즉각 제어 |
| UI | 사용자 입력과 화면 표시 | 장치 장애 판단 |

## 7. 키오스크 장치 이벤트 예시

| 장치 | 이벤트 | 설명 | 권장 우선순위 |
|---|---|---|---:|
| Button | BUTTON_PRESSED | 사용자가 주문 버튼을 누름 | 3 |
| CardReader | CARD_INSERTED | 카드 삽입 감지 | 2 |
| Payment | PAYMENT_APPROVED | 결제 승인 | 2 |
| Payment | PAYMENT_FAILED | 결제 실패 | 2 |
| Printer | PRINT_STARTED | 영수증 출력 시작 | 4 |
| Printer | PRINT_COMPLETED | 영수증 출력 완료 | 4 |
| Printer | PAPER_EMPTY | 용지 부족 또는 없음 | 1 |
| DoorSensor | DOOR_OPENED | 장비 점검 도어 열림 | 1 |
| LED | LED_ON | 상태 표시등 켜짐 | 5 |

## 8. 이벤트 상태 모델

이후 Spring Boot 연동 실습에서는 이벤트를 상태값과 함께 다룹니다.

| 상태 | 의미 |
|---|---|
| WAITING | 처리 대기 |
| PROCESSING | 처리 중 |
| COMPLETED | 처리 완료 |
| FAILED | 처리 실패 |

예를 들어 `PRINT_STARTED` 이벤트가 발생하면 출력 작업은 `PROCESSING` 상태가 됩니다. 출력이 끝나면 `PRINT_COMPLETED` 이벤트로 `COMPLETED`가 됩니다. 프린터 용지가 없으면 `PAPER_EMPTY` 이벤트로 `FAILED` 상태가 됩니다.

## 10. 정리

RTOS는 키오스크 전체를 대체하는 시스템이 아닙니다. RTOS는 장치와 가까운 영역을 안정적으로 처리하고, Spring Boot는 주문과 상태 데이터를 관리합니다.

이 과정의 최종 목표는 두 영역을 연결하여 실제 키오스크처럼 동작하는 구조를 만드는 것입니다.
