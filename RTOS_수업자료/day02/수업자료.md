# 2일차 학생 공유용 자료

## 1. 전체 실습 구조

```text
Windows
  -> WSL2
  -> Ubuntu
  -> ARM GCC
  -> QEMU
  -> bare-metal firmware
  -> UART log
```

3일차에는 이 구조 위에 FreeRTOS Kernel이 추가됩니다.

```text
FreeRTOS Kernel
  -> ARM GCC
  -> FreeRTOS firmware.elf
  -> QEMU
  -> FreeRTOS Task log
```


## 7. 설치하는 도구는 무엇인가

### QEMU

QEMU는 실제 ARM 개발 보드가 없어도 컴퓨터 안에서 CPU와 보드를 흉내 내어 firmware를 실행하는 에뮬레이터입니다. `QEMU`는 전체 프로젝트 이름이고, 이번 실습에서 직접 실행하는 프로그램은 ARM 시스템용 `qemu-system-arm`입니다.

### `qemu-system-arm`

ARM CPU와 메모리, UART 같은 주변 장치를 포함한 **가상 보드 전체**를 실행합니다. 이번 과정에서는 Cortex-M3 기반 `lm3s6965evb` 보드 모델을 선택합니다.

```bash
qemu-system-arm -M lm3s6965evb -cpu cortex-m3 -kernel build/qemu_hello.elf
```

### UART

UART는 임베디드 장치가 바이트 단위로 데이터를 송수신하는 직렬 통신 장치입니다. 실제 보드에서는 USB-시리얼 케이블로 로그를 확인하지만, QEMU에서는 가상 UART를 현재 터미널에 연결할 수 있습니다.

```text
firmware의 UART 출력 -> QEMU 가상 UART -> WSL 터미널
```

`-serial stdio`는 UART 입출력을 터미널의 표준 입출력에 연결하고, `-nographic`은 별도 그래픽 창 없이 터미널에서 실행하게 합니다.

### QEMU 실습과 실제 ARM 보드의 관계

QEMU는 실제 장비가 아니라 **실제 보드의 CPU, 메모리, UART 같은 하드웨어를 소프트웨어로 흉내 내는 프로그램**입니다. 따라서 QEMU에서 익힌 부팅, 레지스터 접근, UART 로그 출력 원리는 실제 ARM 개발 보드에서도 그대로 적용됩니다.

```text
QEMU 실습
firmware -> UART register -> QEMU 가상 UART -> WSL 터미널

실제 ARM 보드
firmware -> UART register -> 실제 UART 하드웨어
         -> USB-UART 케이블 또는 보드 내장 디버거 -> PC 터미널
```

다만 실제 보드에서는 보드에 맞는 UART 레지스터 주소, GPIO 핀, 주변 장치 clock, baud rate를 설정하고 firmware를 Flash에 기록해야 합니다. 즉, **동작 원리는 같고 하드웨어별 초기화와 업로드 과정이 추가됩니다.**

`uart_puts()`는 메시지 전체를 레지스터에 저장하지 않습니다. 문자열을 한 글자씩 `uart_putc()`에 넘기고, `uart_putc()`가 각 문자를 UART 데이터 레지스터에 기록합니다. QEMU는 이 레지스터 접근을 가상 UART 동작으로 처리해 터미널에 전달합니다.

#### UART 출력 흐름을 간단히 이해하기

애플리케이션 코드가 직접 담당하는 일은 다음 두 가지입니다.

1. UART 송신 FIFO가 가득 찼는지 확인합니다.
2. 빈자리가 있으면 `UART_DR`에 문자 하나를 기록합니다.

```c
while ((UART_FR & UART_FR_TXFF) != 0u) {
    /* 송신 FIFO에 빈자리가 생길 때까지 기다립니다. */
}

UART_DR = (uint32_t) ch;
```

FIFO는 `First In, First Out`의 약자로, 먼저 들어간 데이터가 먼저 나오는 큐의 한 종류입니다.

```text
입력: H -> e -> l -> l -> o
출력: H -> e -> l -> l -> o
```

`UART_DR`은 문자열 전체를 보관하는 일반 메모리 버퍼가 아닙니다. 출력할 문자 하나를 UART 하드웨어에 전달하는 데이터 레지스터입니다.

#### `volatile uint32_t`의 의미

UART 레지스터는 다음과 같이 정의되어 있습니다.

```c
#define UART_FR (*(volatile uint32_t *)(UART0_BASE + 0x018u))
```

각 부분의 의미는 다음과 같습니다.

| 코드 | 의미 |
|---|---|
| `uint32_t` | 부호 없는 32비트 정수 자료형 |
| `volatile` | 값이 하드웨어에 의해 언제든 바뀔 수 있으므로 접근할 때마다 실제 주소를 읽거나 쓰도록 지시 |
| `volatile uint32_t *` | 32비트 하드웨어 레지스터를 가리키는 포인터 |
| `(volatile uint32_t *)주소` | 정수로 표현된 주소를 레지스터 포인터로 형변환 |
| `*포인터` | 그 주소에 연결된 레지스터 값을 실제로 읽거나 쓰는 역참조 |

전체 표현식은 다음 순서로 이해할 수 있습니다.

```text
UART0_BASE + 0x018u
  -> 0x4000C018 주소 계산
  -> (volatile uint32_t *)로 32비트 레지스터 포인터 변환
  -> 앞의 *로 해당 주소의 레지스터 접근
```

`uint32_t`를 사용하는 이유는 UART 레지스터를 32비트 단위로 접근하기 위해서입니다. `uint32_t`는 `<stdint.h>`에 정의되어 있으며 크기가 정확히 32비트라는 점이 보장됩니다.

`volatile`이 없다면 컴파일러는 반복해서 같은 값을 읽는 코드를 불필요하다고 판단해 한 번 읽은 값을 재사용할 수 있습니다. 하지만 `UART_FR`은 C 코드가 값을 바꾸지 않아도 UART 하드웨어 또는 QEMU가 FIFO 상태에 따라 값을 변경합니다.

```c
while ((UART_FR & UART_FR_TXFF) != 0u) {
}
```

여기서 `volatile`은 반복할 때마다 `0x4000C018`의 현재 상태를 다시 읽게 합니다.

```text
잘못된 가정:
한 번 읽은 UART_FR 값을 계속 재사용

volatile 사용:
반복할 때마다 UART_FR을 다시 읽음
  -> QEMU 또는 하드웨어가 반환하는 최신 TXFF 상태 확인
```

따라서 `volatile`은 동시 실행 문제를 해결하는 잠금 장치가 아니라, 하드웨어 레지스터 접근을 컴파일러가 임의로 생략하거나 합치지 못하게 하는 표시입니다.

예를 들어 `uart_puts("Hello")`를 호출하면 다음 과정이 문자마다 반복됩니다.

```text
프로그램 메모리의 "Hello\0"
  -> uart_puts()가 'H' 한 글자를 꺼냄
  -> uart_putc('H')
  -> UART_FR의 TXFF 비트 확인
  -> UART_DR에 'H' 기록
  -> QEMU가 가상 UART 송신 FIFO에 추가
  -> QEMU가 FIFO에서 'H'를 꺼냄
  -> -serial stdio를 통해 WSL 터미널에 H 출력
  -> 다음 문자 'e' 처리
```

`UART_FR_TXFF`는 FIFO 상태를 저장하는 변수가 아니라 `UART_FR`의 5번 비트만 확인하기 위한 마스크입니다.

```c
#define UART_FR_TXFF (1u << 5)  /* 0x20 */
```

FIFO 상태에 따른 `TXFF` 값은 다음과 같습니다.

| 송신 FIFO 상태 | `UART_FR`의 `TXFF` |
|---|---:|
| 빈 공간이 있음 | 0 |
| 가득 참 | 1 |

QEMU 환경에서는 QEMU의 가상 UART가 FIFO를 관리하고 현재 상태에 맞는 `UART_FR` 값을 반환합니다. 실제 개발 보드에서는 물리적인 UART 하드웨어가 같은 일을 합니다. 애플리케이션은 `TXFF` 값을 직접 변경하지 않고 읽기만 합니다.

```text
QEMU 환경
애플리케이션 -> UART_DR -> 가상 송신 FIFO -> QEMU -> WSL 터미널

실제 보드
애플리케이션 -> UART_DR -> 물리 송신 FIFO -> UART TX 핀
             -> USB-UART -> PC 터미널
```

### `arm-none-eabi-gcc`

Windows/Ubuntu PC가 아니라 ARM Cortex-M용 코드를 만드는 **크로스 컴파일러**입니다.

| 이름 조각 | 의미 |
|---|---|
| `arm` | ARM 아키텍처용 코드 생성 |
| `none` | Linux나 Windows 같은 운영체제를 대상으로 하지 않음 |
| `eabi` | 임베디드용 ABI 규칙 사용 |
| `gcc` | C/C++ 컴파일러 도구 모음 |

PC용 `gcc`로 만든 프로그램은 x86-64용이므로 Cortex-M3에서 실행할 수 없습니다. 이 실습에서는 `arm-none-eabi-gcc`가 `.c`를 `.o`로 컴파일하고, `linker.ld` 규칙에 따라 최종 `qemu_hello.elf`를 링크합니다.

### Make와 Makefile

`make`는 `Makefile`에 적힌 의존 관계와 명령을 읽어 필요한 빌드 단계만 실행하는 **빌드 실행 도구**입니다.

```text
make       -> 기본 빌드, ELF/BIN 생성
make run   -> ELF가 없으면 빌드한 뒤 QEMU 실행
make clean -> Makefile에 clean 규칙이 있을 때 빌드 결과 삭제
```

`make: No rule to make target 'clean'`은 현재 폴더의 Makefile에 `clean` 규칙이 없거나, Makefile이 있는 프로젝트 폴더가 아닌 곳에서 실행했을 때 발생합니다.

### CMake

CMake는 컴파일러가 아니며 빌드를 직접 수행하는 도구도 아닙니다. `CMakeLists.txt`를 읽고 Makefile 또는 Ninja용 빌드 파일을 **생성**합니다.

```text
CMakeLists.txt -> CMake -> Ninja/Make용 빌드 규칙 -> Ninja/Make -> compiler
```

현재 `qemu-first-sample`은 직접 작성한 Makefile을 사용하므로 CMake가 꼭 필요하지 않습니다. 규모가 커지거나 여러 운영체제와 보드를 지원할 때 CMake를 사용합니다.

### Ninja

Ninja는 Make와 같은 **빌드 실행 도구**입니다. 대규모 프로젝트의 빠른 증분 빌드에 초점을 두며, 보통 CMake가 Ninja용 빌드 파일을 생성합니다.

```bash
cmake -S . -B build -G Ninja
cmake --build build
```

현재 Makefile 예제에서는 Ninja를 사용하지 않지만, 이후 CMake 기반 프로젝트를 이해하기 위해 함께 설치합니다.

### `gdb-multiarch`

여러 CPU 아키텍처를 지원하는 디버거입니다. QEMU를 GDB 서버 모드로 실행한 뒤 접속하면 중단점, 한 줄 실행, 레지스터와 메모리 확인이 가능합니다.

```bash
# 터미널 1: CPU를 멈춘 상태로 QEMU 시작
qemu-system-arm ... -S -gdb tcp::1234

# 터미널 2: ELF의 심볼을 읽고 QEMU에 접속
gdb-multiarch build/qemu_hello.elf
(gdb) target remote :1234
(gdb) break main
(gdb) continue
```

`-S`는 시작 직후 CPU를 멈추고, `-gdb tcp::1234`는 1234 포트에서 GDB 연결을 기다리게 합니다. 2일차 필수 실습은 아니지만 오류 분석에 사용하는 도구입니다.

### 도구가 연결되는 순서

```text
main.c + startup.c + linker.ld
  -> Makefile을 읽은 make
  -> arm-none-eabi-gcc
  -> build/qemu_hello.elf
  -> qemu-system-arm의 가상 Cortex-M3 보드
  -> 가상 UART
  -> WSL 터미널 로그

선택: gdb-multiarch -> QEMU GDB 서버에 연결하여 실행 상태 관찰
선택: CMake -> Makefile 또는 Ninja 빌드 규칙 생성
```

## 11. 2일차와 3일차 차이

| 항목 | 2일차 | 3일차 |
|---|---|---|
| 목적 | QEMU 실행 환경 확인 | 실제 FreeRTOS 실행 |
| 커널 | 없음 | FreeRTOS Kernel |
| scheduler | 없음 | `vTaskStartScheduler()` |
| Task API | 로그만 흉내 | `xTaskCreate()` |
| Queue API | 없음 | `xQueueSend()`, `xQueueReceive()` |

## 실습 과제

1. PowerShell에서 WSL2 상태를 확인합니다.
2. `wsl -d Ubuntu`로 Ubuntu에 접속합니다.
3. Ubuntu에 작업 폴더를 만듭니다.
4. QEMU와 ARM GCC를 설치합니다.
5. `qemu-system-arm -machine help` 결과를 확인합니다.
6. `qemu-first-sample`에서 `make`, `make run`을 실행합니다.
7. 2일차 샘플이 FreeRTOS가 아닌 이유를 한 문장으로 정리합니다.
8. QEMU 환경과 실제 ARM 보드의 UART 출력 경로에서 같은 부분과 달라지는 부분을 각각 한 가지씩 설명합니다.
