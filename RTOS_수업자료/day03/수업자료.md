# 3일차 요약 자료

## 핵심 개념 먼저 보기

| 개념 | 한 문장 설명 | 키오스크 예시 |
|---|---|---|
| Task | Scheduler가 실행 순서를 관리하는 독립 작업 단위 | ButtonTask, PaymentTask, PrinterTask |
| Scheduler | Ready 상태의 Task 중 지금 실행할 Task를 선택 | 높은 우선순위의 버튼 입력을 먼저 실행 |
| Queue | Task 사이에서 구조체 값을 FIFO 순서로 전달하는 대기열 | 주문 이벤트, 출력 요청 전달 |
| Mutex | 한 번에 하나의 Task만 공유 자원을 사용하도록 하는 잠금 | 하나뿐인 프린터 보호 |
| Software Timer | 지정한 시간이 지나면 짧은 callback 실행을 예약하는 커널 객체 | 2초마다 장치 상태 확인 |

### Task의 상태

```text
Ready
  -> Scheduler가 선택
Running
  -> vTaskDelay(), Queue 대기
Blocked
  -> 대기 조건 충족
Ready
```

- `Ready`: CPU를 사용할 준비가 된 상태
- `Running`: 현재 CPU에서 실행 중인 상태
- `Blocked`: Delay, Queue, Mutex 등을 기다리며 CPU를 사용하지 않는 상태

### `vTaskDelay()`가 다른 Task에 실행 기회를 주는 과정

```c
vTaskDelay(pdMS_TO_TICKS(1000));
```

이 코드는 CPU 전체를 1초 동안 멈추거나 잠그는 코드가 아닙니다. 현재 실행 중인
Task만 약 1초 동안 Blocked 상태로 전환합니다.

![vTaskDelay 상태 전환 플로우차트](assets/vtaskdelay-flowchart.png)

```text
ButtonTask 실행 중
  -> vTaskDelay(1000ms) 호출
  -> ButtonTask가 Blocked 상태로 전환
  -> Scheduler가 다른 Ready Task 선택
  -> PaymentTask 또는 PrinterTask 실행
  -> 1초가 지나면 ButtonTask가 Ready 상태로 전환
  -> 우선순위와 실행 조건에 따라 다시 실행
```

1초가 지났다고 ButtonTask가 무조건 그 순간 즉시 실행되는 것은 아닙니다.
Blocked에서 Ready 상태로 바뀐 뒤 Scheduler의 선택을 받아야 다시 실행됩니다.
현재 예제에서는 ButtonTask의 우선순위가 가장 높기 때문에 Ready 상태가 되면
대체로 곧바로 실행됩니다.

### Queue와 Mutex는 목적이 다릅니다

```text
Queue
ButtonTask -> [주문 이벤트] -> PaymentTask
목적: 데이터 전달

Mutex
PrinterTask A -> [프린터 잠금] -> 프린터 사용 -> 잠금 반환
PrinterTask B -> 잠금이 반환될 때까지 대기
목적: 공유 자원 보호
```

`xQueueSend()`는 포인터만 저장하지 않고 `xQueueCreate()`에서 정한 크기만큼
데이터를 Queue 내부에 복사합니다. Mutex는 획득한 Task가 사용 후 반드시
반환해야 하며, 반환하지 않으면 다른 Task가 계속 기다리게 됩니다.

## 핵심 API 사용 방법

### `xTaskCreate()` — Task 생성

```c
BaseType_t xTaskCreate(
    TaskFunction_t taskFunction,
    const char *taskName,
    configSTACK_DEPTH_TYPE stackDepth,
    void *parameters,
    UBaseType_t priority,
    TaskHandle_t *createdTask
);
```

| 인자 | 의미 | 예제 값 |
|---|---|---|
| `taskFunction` | Scheduler가 실행할 Task 함수 | `ButtonTask` |
| `taskName` | 디버깅용 Task 이름 | `"Button"` |
| `stackDepth` | Byte가 아닌 `StackType_t` 개수 | `256` |
| `parameters` | Task 함수로 전달할 값 | `0` |
| `priority` | 숫자가 클수록 높은 우선순위 | `3` |
| `createdTask` | 생성된 Task Handle 저장 위치 | `0` |

성공하면 `pdPASS`를 반환합니다. Task 함수는
`void TaskName(void *parameters)` 형태로 작성하고, 필요한 Task를 모두 생성한
뒤 `vTaskStartScheduler()`를 호출합니다.

### `xQueueSend()` — Queue에 데이터 전송

```c
BaseType_t xQueueSend(
    QueueHandle_t queue,
    const void *itemToQueue,
    TickType_t ticksToWait
);
```

- `queue`: 데이터를 넣을 Queue Handle
- `itemToQueue`: Queue에 복사할 데이터의 주소
- `ticksToWait`: Queue가 가득 찼을 때 공간을 기다릴 최대 Tick 수
- 반환값: 성공 `pdPASS`, 공간이 없으면 `errQUEUE_FULL`

```c
KioskEvent event = { EVENT_ORDER_REQUESTED, "americano x1" };

if (xQueueSend(orderQueue, &event, pdMS_TO_TICKS(100)) != pdPASS) {
    /* 전송 실패 처리 */
}
```

`&event`를 전달하지만 Queue가 주소만 보관하는 것은 아닙니다. Queue 생성 시
지정한 항목 크기만큼 값을 복사합니다. 단, 구조체 안의 문자열 포인터가 가리키는
문자열까지 깊은 복사하지는 않습니다.

### `xQueueReceive()` — Queue에서 데이터 수신

```c
BaseType_t xQueueReceive(
    QueueHandle_t queue,
    void *receiveBuffer,
    TickType_t ticksToWait
);
```

- `queue`: 데이터를 받을 Queue Handle
- `receiveBuffer`: 수신 데이터를 저장할 변수의 주소
- `ticksToWait`: Queue가 비었을 때 데이터를 기다릴 최대 Tick 수
- 반환값: 성공 `pdPASS`, 데이터가 없으면 `errQUEUE_EMPTY`

```c
KioskEvent event;

if (xQueueReceive(orderQueue, &event, portMAX_DELAY) == pdPASS) {
    /* 수신에 성공한 경우에만 event 사용 */
}
```

`portMAX_DELAY`를 사용하면 데이터가 도착할 때까지 Task가 Blocked 상태로
기다립니다. 이 대기 중에는 CPU를 계속 점유하지 않습니다.

### `xSemaphoreTake()` — Mutex 획득

```c
BaseType_t xSemaphoreTake(
    SemaphoreHandle_t mutex,
    TickType_t ticksToWait
);
```

- `mutex`: 획득할 Mutex Handle
- `ticksToWait`: 다른 Task가 사용 중일 때 기다릴 최대 Tick 수
- 반환값: 획득 성공 `pdTRUE`, 실패 `pdFALSE`

Mutex 획득에 성공한 코드 블록 안에서만 공유 자원을 사용합니다.

### `xSemaphoreGive()` — Mutex 반환

```c
BaseType_t xSemaphoreGive(SemaphoreHandle_t mutex);
```

Mutex를 획득한 동일 Task가 공유 자원 사용을 끝낸 직후 호출합니다. 성공하면
`pdTRUE`, 실패하면 `pdFALSE`를 반환합니다.

```c
if (xSemaphoreTake(printerMutex, portMAX_DELAY) == pdPASS) {
    /* 프린터 사용 */
    (void) xSemaphoreGive(printerMutex);
}
```

`xSemaphoreGive()`를 빠뜨리면 다른 Task가 해당 Mutex를 계속 기다리게 됩니다.

### `xTimerStart()` — Software Timer 시작 요청

```c
BaseType_t xTimerStart(
    TimerHandle_t timer,
    TickType_t ticksToWait
);
```

- `timer`: `xTimerCreate()`로 만든 Timer Handle
- `ticksToWait`: Timer 명령 Queue가 가득 찼을 때 기다릴 최대 Tick 수
- 반환값: 시작 명령 전달 성공 `pdPASS`, 실패 `pdFAIL`

```c
TimerHandle_t monitorTimer = xTimerCreate(
    "MonitorTimer",
    pdMS_TO_TICKS(2000),
    pdTRUE,
    0,
    MonitorTimerCallback
);

configASSERT(monitorTimer != 0);
(void) xTimerStart(monitorTimer, 0);
```

`pdPASS`는 callback 실행이 끝났다는 뜻이 아니라 Timer Service Task에
시작 명령을 전달했다는 뜻입니다. Scheduler가 시작된 뒤 주기가 만료되면
callback이 호출됩니다.

### 전체 실행 흐름

![키오스크 통합 예제 플로우차트](assets/kiosk-integrated-flowchart.png)

주문·결제·출력 흐름:

```text
ButtonTask
  -> EVENT_ORDER_REQUESTED 생성
  -> orderQueue에 KioskEvent 값 복사
  -> PaymentTask가 주문 수신
  -> 결제 승인 처리
  -> EVENT_PRINT_REQUESTED 생성
  -> printQueue에 출력 요청 값 복사
  -> PrinterTask가 출력 요청 수신
  -> printerMutex 획득
  -> 영수증 출력
  -> printerMutex 반환
```

장치 모니터링 흐름:

```text
xTimerStart(monitorTimer, 0)
  -> Timer Service Task에 시작 명령 전달
  -> 2000ms 주기 관리
  -> MonitorTimerCallback() 실행
  -> UART로 장치 정상 로그 출력
  -> Auto-reload Timer이므로 다시 2000ms 대기
```

두 흐름은 하나의 긴 함수 안에서 차례로 실행되는 것이 아닙니다. 주문 흐름은
세 사용자 Task와 두 Queue, 하나의 Mutex로 나뉘고, 모니터링 흐름은 FreeRTOS의
Timer Service Task가 관리합니다.

`PaymentTask`는 `orderQueue`가 비었을 때, `PrinterTask`는 `printQueue`가
비었을 때 Blocked 상태로 기다립니다. 따라서 이벤트가 없는 동안 CPU를 계속
소비하지 않습니다.

### 확인할 것

- 주문/결제/출력 흐름이 2단계와 동일하게 동작하는가?
- `MonitorTimer` 로그가 주기적으로 출력되는가?
- Timer callback은 일반 Task와 어떤 점이 다른가?
- 4일차 Spring Boot 연동 시 어떤 이벤트를 서버로 보낼 수 있는가?
- Timer callback에서 오래 걸리는 통신 작업을 직접 수행하면 왜 문제가 되는가?

Timer callback은 FreeRTOS의 timer service task 문맥에서 실행됩니다. callback이
오래 걸리면 다른 Software Timer의 처리도 늦어질 수 있습니다. 긴 작업은
callback에서 직접 수행하지 않고 Queue나 Task notification으로 작업 Task에
전달하는 방식이 좋습니다.

## 실습 과제

### 과제 1. Task 주기 변경

1단계에서 `HeartbeatTask`와 `UiTask`의 `vTaskDelay()` 값을 바꾸고 로그 주기를 비교합니다.

### 과제 2. Queue 길이 변경

2단계에서 `xQueueCreate(4, sizeof(KioskEvent))`의 Queue 길이를 1로 줄이고 동작을 관찰합니다.

### 과제 3. Mutex 제거 실험

2단계 또는 3단계에서 `xSemaphoreTake()`와 `xSemaphoreGive()`를 주석 처리하고, 공유 자원 보호가 왜 필요한지 토론합니다.

### 과제 4. Timer 주기 변경

3단계에서 `MonitorTimer` 주기를 2000ms에서 1000ms로 바꾸고 로그 빈도를 확인합니다.

## 정리

3일차는 실제 FreeRTOS를 사용하지만, 한 번에 모든 기능을 이해하려고 하지 않습니다.

1단계에서 Task 실행을 보고, 2단계에서 이벤트와 공유 자원 보호를 보고, 3단계에서 키오스크 통합 흐름으로 확장합니다.
